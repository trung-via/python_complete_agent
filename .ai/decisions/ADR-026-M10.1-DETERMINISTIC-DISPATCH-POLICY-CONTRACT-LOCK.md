# ADR-026 — M10.1 Deterministic Dispatch Policy Contract Lock

STATUS: LOCKED

## Context

ADR-010 Milestone 10 requires quota-efficient deterministic dispatch before any smart/LLM routing.
M1-M9 have already established canonical state, Brain/Executor-neutral contracts, leases, stable failover, third-executor portability, multi-agent proof, and hot local handoff.

M10 MUST therefore add only zero-token deterministic recommendation policy. It MUST NOT silently expand execution authority.

Baseline for this ADR:

```text
MAIN_SHA: 57a6674887b43e3e91fc01b73479964506b2283e
```

## Decision 1 — M10.1 Is Pure Recommendation Only

M10.1 SHALL implement a pure deterministic dispatcher that returns a recommendation.

It SHALL NOT:
- authorize RUN or FIX;
- acquire/release ExecutorLease;
- mutate runtime authorization/state;
- invoke a Brain or Executor;
- call an LLM or paid API;
- probe vendor quota/account state;
- read environment variables, wall clock, filesystem, network, subprocess, or Git;
- merge or publish.

Human RUN/FIX/MERGE authority remains unchanged.

## Decision 2 — Capacity Snapshot Is Explicit Input

The dispatcher SHALL consume explicit capacity state supplied by the caller.

Canonical capacity states:

```text
AVAILABLE
LIMITED
QUOTA_EXHAUSTED
UNAVAILABLE
UNKNOWN
```

Eligibility semantics:
- AVAILABLE: runnable;
- LIMITED: runnable, but ranked below AVAILABLE at otherwise equal policy rank;
- QUOTA_EXHAUSTED: not runnable;
- UNAVAILABLE: not runnable;
- UNKNOWN: fail-safe not runnable.

M10.1 MUST NOT infer quota from product names, logs, time, previous usage, or vendor heuristics.

## Decision 3 — Capacity Class

Canonical capacity classes:

```text
SUBSCRIPTION
PAID_API
```

Normal M10 selection SHALL prefer SUBSCRIPTION over PAID_API.
PAID_API candidates are ineligible unless the dispatch request explicitly sets `allow_paid_api=True`.
M10.1 may model this class but SHALL NOT invoke the M11 escape hatch.

## Decision 4 — Brain Dispatch Candidate

A Brain candidate SHALL contain:
- exact canonical `brain_id`;
- existing `BrainCapability`;
- `capacity_state`;
- `capacity_class`;
- explicit non-negative `preference_rank`.

Brain compatibility requires:
1. requested `BrainOperation` is supported;
2. if required context bytes are known, `max_context_bytes` is None or large enough;
3. candidate is permitted by capacity class policy.

## Decision 5 — Executor Dispatch Candidate

An Executor candidate SHALL contain:
- exact canonical `executor_id`;
- existing `ExecutorCapabilities`;
- `capacity_state`;
- `capacity_class`;
- explicit non-negative `preference_rank`.

Executor compatibility requires:
1. requested `ExecutionOperation` is supported;
2. every required `ExecutionCapability` is supported;
3. candidate is permitted by capacity class policy.

## Decision 6 — Deterministic Ranking

Among compatible runnable candidates, selection order SHALL be:

```text
1. capacity_class rank: SUBSCRIPTION before PAID_API
2. capacity_state rank: AVAILABLE before LIMITED
3. explicit preference_rank: lower integer wins
4. actor_id: lexical ascending tie-break
```

Input sequence order MUST NOT affect the selected actor.

## Decision 7 — Deterministic Result Status

Canonical result status:

```text
SELECTED
WAIT
NO_COMPATIBLE_CANDIDATE
```

Semantics:
- SELECTED: at least one compatible runnable candidate exists;
- WAIT: at least one policy/capability-compatible candidate exists, but all such candidates are QUOTA_EXHAUSTED, UNAVAILABLE, UNKNOWN, or otherwise not currently runnable;
- NO_COMPATIBLE_CANDIDATE: no candidate satisfies operation/capability/context/class requirements.

A WAIT result SHALL NOT silently fall through to a forbidden paid API candidate.

## Decision 8 — Evidence-Rich Deterministic Output

Dispatch result SHALL include at minimum:
- schema_version;
- actor_kind (`BRAIN` or `EXECUTOR`);
- status;
- selected_actor_id or None;
- machine-readable reason code;
- canonical ordered candidate evaluations;
- deterministic request/policy fingerprint.

Each candidate evaluation SHOULD expose compatibility/runnability and exclusion reason so review does not rely on free-form logs.

## Decision 9 — Fail-Closed Validation

Reject malformed input including:
- duplicate actor IDs;
- candidate actor ID mismatch with embedded capability actor ID;
- negative/bool preference rank;
- duplicate required executor capabilities;
- unknown enum values;
- invalid required context bytes;
- non-canonical actor IDs;
- oversized canonical serialization.

No fuzzy actor matching, case folding, aliases, or nearest-match fallback.

## Decision 10 — Zero-Token / Pure-Function Invariant

The selection functions SHALL be referentially transparent:

```text
same canonical inputs -> same canonical result + same fingerprint
```

No side effects are permitted.

## Decision 11 — Existing Contracts Are Reused, Not Redesigned

M10.1 SHALL reuse:
- `BrainCapability` / `BrainOperation`;
- `ExecutorCapabilities` / `ExecutionOperation` / `ExecutionCapability`;
- `SCHEMA_VERSION` / canonical validation patterns.

M10.1 SHALL NOT modify Brain/Executor request/result semantics, lease semantics, failover proofs, hot-handoff semantics, or Bridge authorization semantics.

## Decision 12 — Human Preference Is Policy Input, Not Authority

`preference_rank` may encode deployment/user policy preference among compatible actors.
It does NOT grant execution authority.

A dispatcher recommendation such as `codex` MUST still be followed by explicit Human authorization before Bridge RUN/FIX activation.

## Decision 13 — M10 Staging

### M10.1
Pure deterministic dispatch contract + tests.

### M10.2
External runtime capacity snapshot integration and a Bridge recommendation/readout surface. No automatic approval or lease mutation.

### M10.3
Operational proof: a real capacity condition (for example `antigravity=QUOTA_EXHAUSTED`, `codex=AVAILABLE`) yields deterministic recommendation; Human then explicitly authorizes the selected Executor and normal Bridge publication proves authority preservation.

## Decision 14 — Required Adversarial Tests

At minimum:

1. identical inputs produce identical result/fingerprint;
2. candidate input order cannot change selection;
3. capability mismatch excludes candidate;
4. required executor capability subset enforced;
5. context-too-large excludes Brain;
6. AVAILABLE outranks LIMITED;
7. QUOTA_EXHAUSTED never selected;
8. UNKNOWN never selected;
9. SUBSCRIPTION outranks PAID_API;
10. PAID_API excluded when `allow_paid_api=False`;
11. WAIT when compatible subscription candidates exist but all are exhausted/unavailable/unknown;
12. NO_COMPATIBLE when no capability-compatible candidate exists;
13. lower preference rank wins;
14. lexical actor-id tie-break is deterministic;
15. duplicate actor IDs reject;
16. embedded capability actor mismatch rejects;
17. bool/negative rank reject;
18. duplicate required capabilities reject;
19. no I/O/clock/network/LLM/store mutation in dispatch implementation;
20. specific executor scenario: antigravity QUOTA_EXHAUSTED + codex AVAILABLE + equal required repo/shell/test capability => codex SELECTED;
21. dispatcher output alone cannot create authorization or lease evidence.

## Acceptance Criteria

M10.1 PASS requires:
- pure deterministic dispatcher implemented in a new continuity module;
- focused adversarial suite green;
- existing Brain/Executor/lease/failover/hot-handoff tests green;
- full repository suite exit 0;
- no Bridge authorization change;
- no paid API invocation path;
- no Human authority change.

M10.1 does NOT prove runtime quota acquisition, M10.2, M10.3, or M11.
