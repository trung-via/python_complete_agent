## Context

TASK-044 attempted the first real E5 zero-copy/paste execution through merged E4 and failed before any executor worktree mutation.

Human-supplied runtime evidence from that failed proof attempt:

```text

```

The installed CLI reports `--ask-for-approval` at the top-level `codex --help` parser and does not report it under `codex exec --help`.

The merged E2 transport currently constructs:

```text
codex exec ... --ask-for-approval never ...
```

and its unit test locks that ordering.

The compatibility defect is therefore in the E2 process argv contract, not in E3 payload composition, E4 authorization/publication semantics, or TASK-044 work instructions.

## Decision

Apply one minimal E2.1 compatibility change:

```text
BEFORE:
codex exec ... --ask-for-approval never ...

AFTER:
codex --ask-for-approval never exec ...
```

Only the location of the exact pair:

```text
--ask-for-approval
never
```

changes relative to the `exec` subcommand boundary.

No other argv element may be added, removed, renamed, reordered, inferred, or made configurable by TASK-045.

## Authority Boundary

E2.1 changes no authority semantics.

```text
recommendation != authorization
authorization != lease
lease != invocation
invocation != receipt
receipt != task success
publication != review PASS
review PASS != merge authorization
```

`--ask-for-approval never` is permitted only because Human authorization and Bridge lease gating occur before E2 invocation. Moving the flag to the correct parser scope must not be interpreted as weakening Human approval requirements.
