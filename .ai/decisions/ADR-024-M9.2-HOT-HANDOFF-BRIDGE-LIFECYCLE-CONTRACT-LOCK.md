# ADR-024 — M9.2 Hot Local Handoff Bridge Lifecycle Contract Lock

STATUS: LOCKED

## Context

ADR-023 / TASK-034 proved M9.1: exact, immutable, non-mutating dirty-workspace checkpoint capture and verification.

M9.2 may now integrate that primitive into AIOS Bridge lifecycle control, but it MUST preserve all existing Human authority, single-active-Executor lease semantics, stable-boundary failover semantics, and publication semantics.

M9.2 is lifecycle integration only. It is NOT the M9.3 real two-Executor hot-handoff proof.

---

## Decision 1 — Human-authorized two-step lifecycle

M9.2 SHALL expose two explicit Human commands:

```text
bridge.py hot-handoff-prepare <task_id> --confirm-quiescent
bridge.py hot-handoff-activate <task_id> --executor <replacement> --checkpoint <fingerprint>
```

`hot-handoff-prepare` means the Human attests that the current source Executor has reached a quiescent boundary and will not continue mutating the workspace.

`hot-handoff-activate` is the distinct Human authorization to continue the same task with the explicitly selected replacement Executor.

No Brain, Executor, quota policy, or Bridge helper may silently select a replacement Executor.

---

## Decision 2 — Supported lifecycle sequence

The only successful M9.2 state sequence is:

```text
ACTIVE(source authorization + source lease)
    ↓ Human --confirm-quiescent
checkpoint capture + immediate verify
    ↓
source lease exact compare-and-release
    ↓
checkpoint re-verify with no active Executor
    ↓
HANDOFF_PREPARED(no active lease)
    ↓ Human explicitly selects replacement + exact checkpoint fingerprint
checkpoint re-verify
    ↓
replacement lease acquire
    ↓
checkpoint re-verify after acquire and before ACTIVE replacement authorization
    ↓
ACTIVE(replacement authorization + replacement lease, checkpoint-bound)
```

There MUST NEVER be two active Executor leases for the same task/workspace.

Checkpoint capture alone does not transfer authority.

---

## Decision 3 — Source authorization binding

Prepare requires an existing exact `ACTIVE` authorization and exact active Executor lease reconstructed from that authorization.

The source authorization must bind:

- task_id;
- action (`RUN` or `FIX`);
- authorized control artifact path/blob;
- target task branch;
- workspace_id;
- source executor_id;
- source lease_id/fingerprint;
- source execution_fingerprint.

The authorized control artifact MUST still match the current control-branch blob before checkpoint preparation.

M9.2 MUST NOT manufacture a task/review authorization when none exists.

---

## Decision 4 — Machine-readable hot-handoff scope

Hot handoff is opt-in per currently authorized control artifact.

The authoritative TASK or REVIEW used by the active authorization MUST contain exactly one machine-readable line:

```text
HOT_HANDOFF_ALLOWED_PATHS_JSON: ["path/one", "path/two"]
```

The value MUST parse as a non-empty JSON array of unique repository-relative POSIX paths.

Bridge MUST use exactly this list as the `allowed_paths` input to the M9.1 primitive.

Forbidden:

- inferring scope from arbitrary Markdown headings;
- widening scope from CLI arguments;
- defaulting to repository root;
- deriving scope from current dirty files;
- nearest-match/fuzzy parsing.

If the marker is missing, duplicated, malformed, empty, or unsafe, prepare fails closed.

---

## Decision 5 — Trusted-control-plane dirty-state exclusion

M9.2 v1 MUST refuse hot handoff if the dirty workspace includes Bridge/runtime modules whose currently executing bytes define handoff authority or verification semantics.

At minimum the protected set is:

```text
bridge.py
src/aios_bridge/runtime_lease.py
src/aios_bridge/continuity/hot_handoff.py
src/aios_bridge/continuity/lease.py
src/aios_bridge/continuity/executor.py
src/aios_bridge/continuity/executor_failover.py
src/aios_bridge/continuity/state.py
src/aios_bridge/continuity/errors.py
```

A task modifying protected control-plane code must use a stable publication boundary rather than hot handoff in M9 v1.

This prevents dirty code from redefining the mechanism that is supposed to prove its own handoff safety.

---

## Decision 6 — Checkpoint persistence

Bridge SHALL use the existing M9.1 content-addressed checkpoint JSON under an external runtime directory derived from the repository runtime root, for example:

```text
<runtime>/hot_handoff/TASK-N/checkpoints/<checkpoint_fingerprint>.json
```

Checkpoint storage MUST remain outside the worktree.

The source authorization after successful prepare SHALL transition from `ACTIVE` to `HANDOFF_PREPARED` and retain exact source/checkpoint provenance sufficient for deterministic activation:

```text
hot_handoff.checkpoint_fingerprint
hot_handoff.allowed_paths
hot_handoff.source_executor_id
hot_handoff.source_lease_id
hot_handoff.source_lease_fingerprint
hot_handoff.source_execution_fingerprint
hot_handoff.authorized_artifact_path
hot_handoff.authorized_artifact_blob_sha
```

Timestamps may be operational metadata but MUST NOT substitute for exact fingerprints.

---

## Decision 7 — Prepare is fail-closed and rollback-safe

Before source lease release, Bridge SHALL:

1. verify current task branch exactly;
2. verify active authorization exactly;
3. verify exact active source lease;
4. verify control artifact blob freshness;
5. parse exact hot-handoff scope marker;
6. reject protected control-plane dirty paths;
7. capture checkpoint;
8. verify checkpoint immediately.

Then Bridge may release only the exact source lease using the existing compare-and-release store.

After release, Bridge MUST verify the same checkpoint again before finalizing `HANDOFF_PREPARED`.

If a normal exception occurs after source release but before prepare finalization, Bridge SHALL attempt fail-closed rollback by reacquiring the exact source lease and restoring the original authorization. If rollback itself cannot be proven, state MUST become `RECOVERY_REQUIRED`; Bridge MUST NOT invent a replacement lease or continue automatically.

No `git stash`, `git reset`, `git clean`, or preservation commit is allowed.

---

## Decision 8 — Activation requires exact prepared provenance

Activation requires:

- authorization status exactly `HANDOFF_PREPARED`;
- no active Executor lease for the task before replacement acquisition;
- explicit supported replacement `--executor`;
- replacement executor different from source executor;
- exact CLI `--checkpoint` equal to prepared checkpoint fingerprint;
- unchanged task branch;
- unchanged workspace_id;
- unchanged authorized control artifact blob;
- exact persisted checkpoint JSON;
- exact workspace verification against checkpoint.

If any condition fails, no replacement lease is acquired.

---

## Decision 9 — Verify before and after replacement lease acquisition

Activation SHALL verify the checkpoint immediately before replacement lease acquisition.

After acquiring the replacement lease, Bridge SHALL verify the same checkpoint again before writing replacement `ACTIVE` authorization.

If the post-acquire verification fails, Bridge MUST compare-and-release the just-acquired replacement lease and leave the handoff in `HANDOFF_PREPARED` when rollback is provable.

The replacement receives mutation authority only after the post-acquire verification succeeds and the new `ACTIVE` authorization is persisted.

---

## Decision 10 — Replacement authorization is a new exact execution binding

Replacement authorization SHALL preserve the original task/action/kind/artifact/branch/workspace boundary but MUST use a newly constructed ExecutorLease and execution fingerprint for the replacement Executor.

The new ACTIVE authorization SHALL retain hot-handoff provenance, including at minimum:

```text
checkpoint_fingerprint
source_executor_id
source_lease_fingerprint
source_execution_fingerprint
replacement_executor_id
replacement_lease_fingerprint
replacement_execution_fingerprint
```

The original source lease MUST NOT be reused as the replacement lease.

---

## Decision 11 — Existing stable-boundary failover remains separate

M9.2 hot handoff metadata MUST NOT be represented as:

- `StableExecutorFailoverProof`;
- M6 failover;
- M8 composite failover proof;
- RESULT publication boundary;
- REVIEW/PASS evidence.

`EXECUTOR_FAILOVER` semantics used by M6/M8 remain unchanged.

M9.2 is unpublished dirty-workspace continuity, not stable-boundary failover.

---

## Decision 12 — Publish behavior

Normal Bridge publish remains the only publication mechanism after replacement continuation.

If ACTIVE authorization contains hot-handoff provenance, publish SHALL fail closed on partial/malformed hot-handoff metadata and SHALL validate the persisted checkpoint object/fingerprint/provenance without requiring the current workspace to still equal the checkpoint (the replacement is expected to have continued editing after activation).

RESULT MAY record auditable M9 lifecycle evidence such as:

```text
HOT_HANDOFF: YES
HOT_HANDOFF_CHECKPOINT_FINGERPRINT: <sha256>
HOT_HANDOFF_FROM_EXECUTOR: <source>
HOT_HANDOFF_TO_EXECUTOR: <replacement>
```

These fields are evidence only. They do not claim M9.3 real-proof PASS.

---

## Decision 13 — Context visibility

`bridge.py context <task_id>` SHOULD surface prepared/active hot-handoff metadata so the Human and replacement Executor can see the exact checkpoint and source/replacement identities.

Context output MUST NOT expose secrets or hidden reasoning.

---

## Decision 14 — M9.2 does not require changes to lease contracts

Existing `ExecutorLease`, `AtomicExecutorLeaseStore.acquire()`, `require_active()`, and compare-and-release `release()` remain authoritative.

M9.2 MUST NOT redesign:

```text
src/aios_bridge/continuity/lease.py
src/aios_bridge/runtime_lease.py
```

If implementation discovers that these existing primitives are insufficient, TASK-035 must stop and report a blocker rather than silently changing M5 lease semantics.

---

## Decision 15 — Required adversarial coverage

M9.2 tests SHALL cover at minimum:

1. prepare requires explicit `--confirm-quiescent`;
2. prepare requires ACTIVE authorization;
3. source active lease must exactly match authorization;
4. control artifact blob drift blocks prepare;
5. missing/duplicate/malformed hot-handoff scope marker blocks prepare;
6. protected control-plane dirty path blocks prepare;
7. checkpoint capture/verification failure leaves source lease/auth intact;
8. successful prepare releases source lease and leaves authorization `HANDOFF_PREPARED`;
9. post-release verification failure rolls source lease/auth back when possible;
10. activation requires explicit replacement executor;
11. same source/replacement executor is rejected;
12. wrong checkpoint fingerprint is rejected;
13. workspace drift before activation is rejected;
14. control artifact drift before activation is rejected;
15. activation requires no active lease;
16. successful activation creates a new replacement lease and ACTIVE replacement authorization;
17. post-acquire checkpoint verification failure releases replacement lease and preserves prepared state;
18. two active leases are never observable in tested lifecycle transitions;
19. source authorization cannot publish after successful prepare;
20. partial/malformed hot-handoff metadata blocks publication;
21. normal non-hot-handoff RUN/FIX behavior remains unchanged;
22. no M6/M8 failover proof is manufactured.

---

## Decision 16 — M9.2 acceptance boundary

M9.2 PASS proves only that Bridge can safely prepare and activate a checkpoint-bound hot-handoff lifecycle under Human control.

It does NOT prove that two real distinct Executors successfully continued the same unpublished task.

That proof belongs exclusively to M9.3.

---

## Locked Summary

```text
Human confirms source quiescent
        ↓
Bridge validates ACTIVE auth + exact source lease + exact control scope
        ↓
M9.1 checkpoint capture + verify
        ↓
exact source lease release
        ↓
checkpoint verify again
        ↓
HANDOFF_PREPARED / zero active executors
        ↓
Human explicitly selects distinct replacement + exact checkpoint
        ↓
checkpoint verify
        ↓
new replacement lease acquire
        ↓
checkpoint verify again
        ↓
ACTIVE replacement authorization
        ↓
replacement may continue task
        ↓
normal Bridge publish later
```

Human authority, exact workspace evidence, and `MAX_ACTIVE_EXECUTORS_PER_TASK = 1` remain invariant.
