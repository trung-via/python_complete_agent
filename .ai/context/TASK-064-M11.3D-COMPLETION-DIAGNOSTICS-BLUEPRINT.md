## Problem Statement

M11.3C is operationally proven: the live paid-Brain path no longer fails at the previous hard-coded ~30 second timeout. Live attempt #2 used a 120-second timeout and returned provider evidence in 15.287 seconds.

The new failure is independent of timeout. MiniMax-M3 consumed the exact 2000-token completion allowance and returned `finish_reason=length`; the provider adapter correctly normalized this as `INVALID_RESPONSE / TRUNCATED_OUTPUT`. The grant remained one-shot and durably CONSUMED, the usage ledger contained exactly one record, and no successful proposal/proof artifact was published.

A local-only forensic also proved exact full provider-input correlation: local count 3155 == provider-reported prompt_tokens 3155.

## Post-Consume Diagnostic Contract

Current failure output `OPERATIONAL_PROOF_FAILED_AFTER_CONSUME` is safe but too coarse. TASK-064 must add a bounded, allowlisted diagnostic for the case where the single provider call completed and produced a non-SUCCESS normalized response after durable grant consumption.

Required semantic shape:

```text
POST_CONSUME_RESPONSE_REJECTED
STATUS=<allowlisted ModelResponseStatus value>
ERROR_CODE=<allowlisted bounded code or OTHER>
GRANT_CONSUMED=YES
RETRY_COUNT=0
```

The diagnostic MUST NOT include:

```text
response content
reasoning content
prompt/context content
error_message
raw provider request ID
credential/header/cookie/API key
local absolute path
raw provider response body
```

At minimum the allowlist must preserve safe classification for:

```text
TRUNCATED_OUTPUT
INVALID_ARTIFACT_STRUCTURE
CORRELATION_ERROR
MALFORMED_RESPONSE
EMPTY_CONTENT
TIMEOUT
AUTH_ERROR
RATE_LIMITED
UNAVAILABLE
```

Unknown or provider-specific unbounded codes must collapse to `OTHER` rather than being echoed.

A non-SUCCESS response MUST still fail. Diagnostics improve observability only; they grant no proof authority.

## Reasoning-Token Telemetry Scope Split

Live forensic showed `provider_reasoning_tokens` is currently unavailable in the ledger. `UsageRecord` already has a field for it, but `ModelResponse` does not currently carry reasoning-token telemetry and `ModelGateway` therefore cannot propagate it.

Adding this telemetry would require a cross-cutting response-contract/schema change touching provider normalization, `ModelResponse`, Gateway propagation, serialization/tests, and compatibility surfaces.

Therefore:

```text
TASK-064_REASONING_TOKEN_SCHEMA_CHANGE: FORBIDDEN
POTENTIAL_FOLLOWUP: TASK-065 / M11.3E, only if still useful after successful proof
```

This split prevents TASK-064 from becoming a broad schema migration while a paid-runtime proof is still being hardened.
