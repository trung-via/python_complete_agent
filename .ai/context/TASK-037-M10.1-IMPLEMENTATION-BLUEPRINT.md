## 6. Candidate evaluation

Implement frozen generic evidence model:

```python
@dataclass(frozen=True)
class CandidateEvaluation:
    actor_id: str
    compatible: bool
    runnable: bool
    reasons: tuple[CandidateReason, ...]
    capacity_class: CapacityClass
    capacity_state: CapacityState
    preference_rank: int
```

Canonical reasons must be deterministically ordered. `ELIGIBLE` may be the only reason for fully AVAILABLE candidates; LIMITED should include `CAPACITY_LIMITED` while remaining runnable.

For non-runnable capacity states, compatibility remains true if operation/capability/context/class policy matched; `runnable=False` with capacity reason. This distinction drives WAIT.

## 7. Dispatch result

Implement frozen:

```python
@dataclass(frozen=True)
class DispatchResult:
    actor_kind: DispatchActorKind
    status: DispatchStatus
    selected_actor_id: str | None
    reason: DispatchReason
    request_fingerprint: str
    evaluations: tuple[CandidateEvaluation, ...]

```

Invariant:
- SELECTED requires selected_actor_id present and matching one runnable compatible evaluation;
- WAIT / NO_COMPATIBLE require selected_actor_id=None;
- evaluations canonical sorted by `actor_id`;
- `to_dict`, `to_canonical_json`, `fingerprint`.

## 9. Brain evaluation algorithm

`dispatch_brain(request: BrainDispatchRequest) -> DispatchResult`

For each candidate:
1. operation supported? else incompatible `OPERATION_UNSUPPORTED`;
2. if required_context_bytes not None and capability.max_context_bytes is not None and too small -> incompatible `CONTEXT_TOO_LARGE`;
3. if PAID_API and `allow_paid_api=False` -> incompatible `PAID_API_NOT_ALLOWED`;
4. capacity:
   - AVAILABLE => runnable;
   - LIMITED => runnable with `CAPACITY_LIMITED`;
   - QUOTA_EXHAUSTED => compatible, not runnable;
   - UNAVAILABLE => compatible, not runnable;
   - UNKNOWN => compatible, not runnable.

Then:
- any runnable compatible -> rank/select -> SELECTED;
- else any compatible -> WAIT;
- else -> NO_COMPATIBLE_CANDIDATE.

## 10. Executor evaluation algorithm

`dispatch_executor(request: ExecutorDispatchRequest) -> DispatchResult`

For each candidate:
1. operation supported? else incompatible;
2. required capabilities must be subset of candidate supported capabilities; otherwise `REQUIRED_CAPABILITY_MISSING`;
3. PAID_API gate;
4. same capacity logic as Brain.

Then same status selection logic.
